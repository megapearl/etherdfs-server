EtherDFS changelog history

--- Donald Flissinger fork ---

v1.1.4 [2026-07-14] -- harden the LFN layer against non-path operands:
 - fix(client): a central guard at the top of the 71xx dispatch now rejects
   operands that cannot be a DOS path (no NUL within 260 bytes, or embedded
   control bytes) with "path not found" when they would bind to an EtherDFS
   drive. Wire captures proved such calls happen in the wild (a caller's
   delimiter table, TAB included, arrived as a 7141h/7143h "path" and left
   as a garbage TRUENAME frame). Accepting them was harmful both ways:
   claiming let 7160h CL=0 copy hundreds of garbage bytes into the caller's
   buffer, chaining handed DOSLFN an operation it mis-runs as local FAT on a
   sectorless drive (the class behind the old MD hang). Prime suspect for the
   memory-layout-dependent hard hang when copying OFF the mapped drive with
   DOS Navigator F5 or 4DOS COPY (COMMAND.COM COPY, which never enters the
   LFN dispatch, always worked).
 - fix(client): 7160h TRUENAME CL=0 could write its terminating NUL at byte
   261 of the caller's 260-byte buffer (indices 0..259; the CL=1/2 sibling
   already capped correctly). Off-by-one, now bounded to dst[259].
 - fix(client): getcds() accepted a drive index one past LASTDRIVE (a COUNT,
   so valid indices are 0..count-1). Latent, install/unload path only.
 - hardening: resident stack grown from ~1.5K to ~3K (DATASEGSZ 4608 -> 6144;
   +1.5K resident, typically UMB). Hardware IRQs nest on this stack while
   sendquery busy-waits with interrupts enabled; the measured high-water left
   ~660 bytes of margin, which is margin but not comfort.

v1.1.3 [2026-07-14] -- relative LFN paths resolve against the right drive:
 - fix(client): a bare relative path ("file.txt") in an LFN INT 21h call is now
   always resolved against the DEFAULT drive (SDA 16h), and its current
   directory is read from that drive's OWN CDS, taken from the DOS List of
   Lists at install. The client used to derive the CWD from the SDA's
   drive_cdsptr, which is the CDS of the drive of the CURRENT DOS OPERATION:
   after an application touched another drive it pointed at THAT drive, the
   "is this CDS really mine?" guard failed, and the client declined the call --
   handing it to DOSLFN, which mangles it for our PHYSICAL-flagged redirector.
   Symptom: Norton Commander's F3 viewer reported "file not found" for every
   file on the mapped drive (it opens C:\APPS\NC\NCVIEW.MSG and only THEN asks
   for the true name of the bare relative filename -- so drive_cdsptr pointed at
   C: while the default drive was ours). F4 worked because it passed a qualified
   path. Verified on real hardware: F3 now views files on the mapped drive.
   This affects every LFN handler that takes a relative path, not just truename.

v1.1.2 [2026-07-08] -- directory-creation fixes for DOS file managers:
 - fix(client): 7160h TRUENAME CL=0 now canonicalizes a RELATIVE path to an
   absolute one ("X:" + the drive's current directory from the CDS) instead of
   returning it unchanged (uppercased). DOS Navigator OSP 6.4.0 (DPMI build)
   expands the F7 "make directory" name through this call and aborted silently
   when the result carried no drive letter, so F7 with a relative name did
   nothing on an EtherDFS drive (no dir, no error, zero DOS calls). Already
   drive-qualified and UNC paths keep the uppercase-as-is behavior that 4DOS's
   mkfname relies on. Verified on real hardware, in the root and in subdirs.
 - fix(client): a legacy AH=39h MkDir of a drive-qualified path on an EtherDFS
   drive is rerouted to its LFN twin 7139h before DOSLFN sees it, so
   "MD E:\DIR" (COMMAND.COM/batch/Borland RTL) no longer hangs in DOSLFN's
   direct-sector VFAT write on our sectorless redirector drive. Verified:
   drive-qualified and relative MD, and RD, all work.
 - build: ships rebuilt static ethersrv binaries (the v1.1.1 lfn2sfn server
   change had not been folded into the committed binaries).

v1.1.1 [2026-07-06] -- relative-path LFN resolution + standard 8.3 aliases:
 - client: resolve current-drive-relative and CWD-relative paths in every LFN
   INT 21h handler (714Eh findfirst, 716Ch open/create, 7141h delete, 7156h
   rename, 7139h mkdir, 713A/3Bh rmdir/chdir, 7143h attrs, 7160h truename)
   instead of only claiming drive-qualified ("X:\") paths. Without this, once
   our drive was the CURRENT DOS drive the shell/DOSLFN handed us drive-less
   paths that we declined: VC showed short names in subdirectories and 7-Zip
   could not open long-named files. New helpers lfn_claimdrv() and
   lfn_server_path() centralize the resolution.
 - server: lfn2sfn() follows the Win95/DOSLFN standard 8.3 algorithm: only a
   lossy basis gets a "~N" numeric tail; names that already fit 8.3 keep their
   plain form. Fixes alias inconsistency for multi-dot names ("a.b.c.gz" ->
   "ABC~1.GZ") and matches what DOSLFN and Windows generate.
 - deployment: load DOSLFN with "f-" (fallback-off) and etherdfs AFTER it.

v1.1.0 [2026-07-05] -- first stable release with native Long File Name support:
 - Full Win95-style LFN on the mapped drive (client TSR hooking INT 21h/71xx +
   additive server wire-opcodes 0x40-0x4E): DIR shows real long names; open/
   copy/REN/DEL/MD/RD/CD/ATTRIB/truename accept long names and long directory
   components. Classic 8.3 path unchanged (backward compatible).
 - OEM codepage conversion (CP437 default, CP850 via ETHERDFS_CODEPAGE): names
   are UTF-8 on disk, OEM on the wire; 8.3 aliases kept 7-bit so they survive
   DOS filename normalization. DOSLFN coexistence (load DOSLFN first).
 - Hardening: clamped legacy path copies, no silent-drop on short LFN payloads,
   case-duplicate mkdir/rename rejection, correct top-of-chain /U unload check.
 - Validated on real hardware (PC DOS 7.10 + 4DOS 8.00 + Norton/Volkov).


fork [2026-07-02] -- native LFN, Phase-2 increment 3: open/create with long
names (validated on real hardware; open/type/copy/create of long-named files
now work, not just DIR):
 - feat: INT 21h/AX=716Ch (LFN create-or-open) for our own drives. The client
   resolves the long name to its 8.3 alias via the server (AL_LFN_OPEN 0x43 as
   an existence probe; AL_LFN_CREATE 0x44 when the Win95 action word requires
   create/truncate -- which lands the file under its REAL long name and applies
   the create attributes server-side), then PASSES DOWN a classic INT 21h/AX=
   6C00h open of the alias path to the previous INT 21h handler. DOS allocates
   the JFT/SFT/handle itself and routes through our proven INT 2Fh redirector,
   so read/write/seek/close ride the existing 8.3 path with no SFT work in the
   client. Falls back to classic 3Dh open if a kernel lacks 6C00h. The action-
   taken (1 opened / 2 created / 3 replaced) is synthesized client-side because
   6C00h has documented CX-return kernel bugs on redirector drives.
   Pass-down mechanics: 'pushf;cli;call dword ptr glob_prev21call' (m16:16, set
   at install, offset-low/segment-high like the packet-driver call); the server
   round-trip runs first on the resident stack, then the pass-down runs AFTER
   the caller stack is restored so the nested 2Fh open is not seen as SS==DS by
   the reentrancy guard.
 - feat(server): Win95 long-name matching for the LFN find opcodes (matchlfn2
   mask): an exact long leaf with spaces/>8-char base/multiple dots/~N alias, or
   a mid-name wildcard, now matches (previously findfile only FCB-matched the
   8.3 alias, so "Games List.txt" was unfindable -- which the 716Ch alias probe
   needs). FINDNEXT gained an optional additive LFNSTR mask tail; legacy 8.3
   opcodes pass NULL and are byte-identical to before.
 - scope note: only the leaf name is alias-translated; a path with LONG
   intermediate directory components needs a future truename (7160h) op --
   parents must be 8.3-clean for now. Copying a long name to a NON-LFN drive
   (e.g. local C:) truncates to 8.3 -- that is the target drive's limitation,
   not ours; copy to another EtherDFS drive preserves the long name.
 - fix: DATASEGSZ 4096 -> 4608 for the increment-3 globals (find-slot long
   masks, pass-down path buffer); verified against the linker map (DGROUP 4064,
   ~1566 bytes resident stack). Pass-down path always keeps the "X:" drive
   prefix so it resolves against OUR drive, never the process default drive.
 - tests: server exact/wildcard long-name matching + FindNext-with-mask-tail
   regression (test_proto.c); fixture gains "my long file.txt".

fork [2026-07-02] -- native LFN, Phase-2 increment 2 (validated on real
hardware: PC DOS 7.10 + 4DOS 8.00 + EMM386, with Win95LFN=Yes):
 - feat: DIR on an EtherDFS drive under an LFN-aware shell now shows REAL long
   filenames (mixed case, spaces), with sizes and dates. The INT 21h hook
   services the Win95 LFN API for our own drives: 71A0h volume info (local,
   advertises LFN via BX bit14), 714Eh FindFirstFile / 714Fh FindNextFile
   (server round-trip via the new additive opcodes 0x41/0x42, filling the
   caller's 318-byte WIN32_FIND_DATA: long name @0x2C, 8.3 alias @0x130,
   FILETIME or DOS-packed times per SI), 71A1h FindClose, and 71A7h
   FILETIME<->DOS date/time conversion (pure local math, both directions).
   A 4-slot find-handle table (handles 0xEF00|slot) keeps search state
   client-side; foreign handles and other drives chain to the previous
   handler. Everything 8.3 (COMMAND.COM, the INT 2Fh redirector) is untouched
   and re-validated.
 - The blocking server round-trip from the INT 21h hook reuses the proven
   INT 2Fh stack-switch discipline (own save slots) plus a STATELESS nesting
   guard: a handler entered with SS already == DS is nested inside an outer
   switched context and bails/chains instead of resetting the shared resident
   stack. (An earlier flag-based guard could get stuck and killed all 2Fh
   service.)
 - fix: DATASEGSZ 3500 -> 4096. The resident-segment copy must cover the
   WHOLE DGROUP including the transient stack: main()'s parsed args live near
   the stack top and arrived as garbage after the switch, silently dropping
   the auto-discovery flag (server MAC 00:00:00:00:00:00, empty DIR).
 - fix: the installer's DS-relocation patch for the INT 2Fh handler now scans
   for the "MVet" signature (like the INT 21h "MV21" patch) instead of using
   a hardcoded offset that broke whenever the prologue shifted ("DS/SS
   relocation failed"). The install failure path also switches back to the
   original stack before freeing the new segment (it used to free the segment
   its own SS lived in: hang / EMM386 #12 stack fault).
 - fix: Win95 wildcard semantics for LFN masks on the client FINDNEXT
   template ('*' with no dot also wildcards the extension field, and the
   extension scan stops at a second dot) -- byte-identical to the server's
   lfn_mask2fcb, verified by a 17k-mask fuzz harness. Without this, DIR
   listed only directories ("dir" vs "dir *.*" differed).
 - tests: FTCONV.H golden vectors + an exhaustive 46751-date round-trip sweep
   (tests/test_ftconv.c); client/server mask-identity fuzz; the server wire
   test gained a mask-"*" regression that fails the build if files with
   extensions are dropped.

fork [2026-07-01]:
 - fix: DIR under 4DOS now lists files. 4DOS's DIR queries free space
   (INT 21h/AH=36h, and INT 21h/AX=7303h on PC DOS 7.x) BEFORE the listing and
   aborts the whole listing if it gets AX=0xFFFF (invalid drive). DOS answers
   AH=36h locally for our PHYSICAL-flagged redirector drive and never routes it
   to us, returning 0xFFFF. The client now answers AH=36h for its own drives
   directly with a valid volume, so 4DOS proceeds to the file enumeration.
   COMMAND.COM was unaffected (it ignored the bad free-space and listed anyway).
 - fix: DIR "bytes free" footer now shows for our drives under both shells. The
   AH=36h answer above already gives 4DOS its footer, but PC DOS 7.x COMMAND.COM
   (and 4DOS itself) queries free space via INT 21h/AX=7303h (Win95 extended
   free space) first. The client now fills the 7303h ExtGetDskFreSpcStruc for
   its own drives with the same figures instead of failing it, so COMMAND.COM
   also gets a footer. Non-our drives chain to DOS unchanged.
 - fix: the footer now also shows under COMMAND.COM when the CURRENT drive is
   our drive. In that case DIR queries free space with AH=36h/DL=0 (the default
   drive) rather than an explicit drive number; the client now resolves the
   current drive from the SDA (offset 16h) and answers DL=0 for its own drives.
 - feat: report a synthetic volume serial number via INT 21h/AX=6900h, so DIR
   shows a "Volume Serial Number" line for our drives: EDF5-xxxx (high word =
   the EtherDFS ethertype 0xEDF5, low word = the last two bytes of the server
   MAC). Note: 4DOS skips the serial query for network drives, so this surfaces
   under COMMAND.COM. Non-our drives chain to DOS unchanged.
 - fix(server): synthetic volume label is opt-in (only when a label is set).
 - fix(server): expand '*' wildcard to '?' in filename2fcb (FCB mask
   expansion), fixing "dir e:\" under COMMAND.COM.
 - fix(client): drop the doubled 'v' in the version banner.

--- upstream (Mateusz Viste) ---

v0.8.2 [2018-02-03]:
 - support for lock/unlock operations (INT 2Fh,110Ah).

v0.8.1 [2017-04-16]:
 - EtherDFS frames are validated by a cksum (can be disabled with /n),
 - EDF5 frames announce their length to avoid troubles with Ethernet padding,
 - arguments can be passed in any order,
 - /q and /u can be used together.

v0.8 [2017-03-04]:
 - improved self-detection to avoid loading EtherDFS twice,
 - added unloading support (/u),
 - fixed a FindFirst regression (fixes usage under 4DOS),
 - fixed SETATTR action when using a non-FreeDOS attrib command,
 - implemented the 'Seek From End' call,
 - minor memory optimizations,
 - makes sure the redirector API is available before installing,
 - support for multiple drive mappings.

v0.7 [2017-02-11]:
 - MS-DOS compat: flagging newly mapped drive so MS-DOS doesn't ignore it,
 - fixed FindNext behavior so it's compatible with ATTRIB from MS-DOS,
 - implemented the "Special Open" call (used by COPY in MSDOS 5.0 and 6.x),
 - increased timeout retries from 3 to 5 (more reliable on lossy networks),
 - fixed parsing of the MAC address provided on command-line,
 - minor speed optimizations.

v0.6 [2017-02-05]:
 - significantly reduced EtherDFS resident footprint (16K -> 7K),
 - fixed GETATTR (was returning garbage),
 - added support for 'CLOSE FILE', 'RENAME FILE' and 'SET ATTRIBS' actions.

v0.5 [2017-01-31]:
 - first public release.
